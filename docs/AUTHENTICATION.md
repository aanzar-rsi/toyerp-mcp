# Authentication, Users, Permissions, and Agent Connections

This guide covers the complete security setup for the toy ERP: creating the
authentication tables, provisioning the default administrator, creating users,
assigning tool permissions, obtaining and revoking tokens, and connecting an
MCP-capable agent.

> This is a test ERP, not a production identity provider. It has local users,
> one-hour opaque bearer tokens, and SQLite-backed authorization. It does not
> implement OAuth authorization-code flows, SSO, MFA, token refresh, password
> recovery, or service-account keys.

## 1. Security model at a glance

The HTTP origin exposes three kinds of routes:

| Route | Purpose | Authentication |
| --- | --- | --- |
| `POST /auth/login` | Exchange username/password for a token | None |
| `POST /auth/logout` | Revoke the current token | Bearer token |
| `POST /admin/{operation}` | Manage users, roles, and grants | Admin bearer token |
| `/mcp` | List and call MCP tools | Bearer token |

The server does not send passwords to MCP tools. Login happens over HTTP first;
the resulting token is then sent in `Authorization: Bearer <token>` on every MCP
HTTP request.

Permission resolution is:

1. An active administrator can see and call every registered `BAPI_*` tool.
2. A non-admin receives the union of all tools granted to their roles.
3. A user-specific allow or deny overrides the role result for that tool.
4. The server filters `tools/list` and separately checks every `tools/call`.

This means hiding a tool is not the security boundary by itself: invocation is
also denied if a client tries to call a tool name it was not shown.

## 2. Create or upgrade the authentication tables

### Fresh database

Do not create the tables manually. On first startup, `server.entrypoint` calls
`init_schema()`, which applies `data/schema.sql`. That schema includes all
security tables. It then seeds ERP business data and records the current schema
version.

Docker:

```bash
cp .env.example .env
docker compose up --build
```

Local Python:

```bash
python -m venv .venv
source .venv/bin/activate        # Windows PowerShell: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
python -m server.entrypoint
```

### Existing pre-authentication database

Startup always calls `migrate_schema()`. An older database at schema version 1
receives `data/migration_002.sql`, which creates the security tables without
replacing existing ERP data. Migration state is stored in SQLite's
`PRAGMA user_version`.

Before upgrading data you care about, stop writers and back up the SQLite file:

```bash
# Local installation
cp data/erp.db data/erp.db.backup

# Docker named volume: copy the database out of the running service
docker compose cp toy-erp:/data/erp.db ./erp.db.backup
```

Then start the current application normally. Migrations are automatic and
idempotent at the version level. Run the tests before using a copied production
or shared database:

```bash
pytest tests/
```

### What each security table stores

| Table | Contents |
| --- | --- |
| `users` | Username, password hash, admin/active flags, failed-login and lockout state |
| `roles` | Named permission groups |
| `user_roles` | Many-to-many user/role assignments |
| `role_tools` | MCP tool names granted to roles |
| `user_tools` | Per-user tool overrides (`allowed` is 1 or 0) |
| `sessions` | SHA-256 token hash, owner, expiry, and revocation flag |
| `security_events` | Login, admin, tool-call, and denial audit events |

You can verify the schema version and tables without installing the SQLite CLI:

```bash
python -c "import sqlite3; c=sqlite3.connect('data/erp.db'); print('version:', c.execute('PRAGMA user_version').fetchone()[0]); print([r[0] for r in c.execute(\"SELECT name FROM sqlite_master WHERE type='table' AND name IN ('users','roles','user_roles','role_tools','user_tools','sessions','security_events') ORDER BY name\")])"
```

For Docker's named volume, run the equivalent inside the service:

```bash
docker compose exec toy-erp python -c "import sqlite3; c=sqlite3.connect('/data/erp.db'); print('version:', c.execute('PRAGMA user_version').fetchone()[0]); print([r[0] for r in c.execute(\"SELECT name FROM sqlite_master WHERE type='table' AND name IN ('users','roles','user_roles','role_tools','user_tools','sessions','security_events') ORDER BY name\")])"
```

The current expected schema version is `3`, and both commands should print all
seven security table names.

Foreign keys cascade from users and roles into their assignments. The database
never stores a plaintext password or plaintext bearer token.

Do **not** insert users with raw SQL. `users.password_hash` must contain the
format generated by `server.security.password_hash()`, and direct writes bypass
validation and audit events. Use startup provisioning and the admin API.

## 3. Configure and start the server

The relevant environment variables are:

| Variable | Docker default | Meaning |
| --- | --- | --- |
| `DB_PATH` | `/data/erp.db` | SQLite database file |
| `MCP_HOST` | `0.0.0.0` | Server bind address |
| `MCP_PORT` | `8000` | Server port |
| `ERP_PUBLIC_URL` | `http://127.0.0.1:8000` | Public origin used in MCP auth metadata |

`ERP_PUBLIC_URL` is an origin, not an MCP path: use
`https://erp.example.com`, not `https://erp.example.com/mcp`. Plain HTTP is
accepted only for `localhost`, `127.0.0.1`, or `::1`. A remotely reachable
installation must use HTTPS.

Docker Compose publishes the service on localhost by default:

```text
127.0.0.1:8000 -> container:8000
```

That is appropriate for local agent testing. For remote agents, place an HTTPS
reverse proxy in front, set `ERP_PUBLIC_URL` to its external origin, route
`/auth/*`, `/admin/*`, and `/mcp` to this service, and keep the container port
private.

## 4. Default users and role groups

On every startup, the server reads `scripts/default_users.txt`. Each non-comment
row has `username|password|role`; `ADMIN` creates an administrator and a standard
role name assigns that team access:

```text
ahad-anzar|a-unique-long-password|ADMIN
hr-user|another-unique-long-password|HR_ALL
```

Provisioning creates missing users and role assignments but never replaces an
existing password. The checked-in credentials are only for a local toy
environment; change them before first startup and never expose them publicly.

Configured usernames must:

- be 3-64 characters;
- start with an ASCII letter; and
- contain only letters, digits, `.`, `_`, or `-`.

Passwords must contain 12-1024 characters. They are salted and hashed with
PBKDF2-HMAC-SHA256 using 600,000 iterations. Prefer a unique password-manager
generated password or long passphrase.

Startup also creates these reusable groups and adds any missing standard grants:

| Role | Access |
| --- | --- |
| `HR_ALL` | All HR, leave, and payroll tools |
| `FINANCE_ALL` | AP, AR, invoices, GL journals, accounts, and summaries |
| `PROCUREMENT_ALL` | Vendors, materials, stock, purchase orders, and goods receipts |
| `SALES_ALL` | Customers, sales orders, AR invoices, and incoming AR payments |
| `INVENTORY_ALL` | Materials, stock, and goods receipts |
| `MASTER_DATA_ALL` | Vendor, customer, and material tools |
| `ERP_READ_ONLY` | All `GETLIST`, `GETDETAIL`, and summary tools |

Provisioning is idempotent: it keeps existing users, passwords, role assignments,
custom roles, and grants. It only creates the default admin when absent and adds
missing default roles/grants.

## 5. Use the administration helper

The repository includes `scripts/erp_admin.py`. It calls the same supported
HTTP endpoints an external administrator would use and does not access SQLite
directly. Run it from the repository root:

```bash
python scripts/erp_admin.py --help
```

Set defaults if the service is not local:

```bash
export ERP_URL=https://erp.example.com
export ERP_ADMIN_USER=admin
```

The script prompts for passwords with terminal echo disabled. It never accepts
passwords as command-line arguments. For each admin command it logs in, performs
the operation, and logs out. If `ERP_ADMIN_TOKEN` is set, it uses that token and
does not revoke it afterward.

### Create a user and assign a standard role

The smallest useful least-privilege setup for a read-only purchasing agent is:

```bash
python scripts/erp_admin.py create-user purchasing-agent
python scripts/erp_admin.py assign-role purchasing-agent PROCUREMENT_ALL
```

The new user initially has no tools until a standard or custom role is assigned.

Tool names are exact and case-sensitive. Use an administrator account with
`scripts/mcp_client.py` to list all currently registered names, or use the tool
list in `README.md`.

### User lifecycle commands

```bash
# Create a non-admin user; prompts twice for the new password
python scripts/erp_admin.py create-user USERNAME

# Replace password, clear lockout state, and revoke all existing sessions
python scripts/erp_admin.py reset-password USERNAME

# Disable and revoke sessions, or enable future logins again
python scripts/erp_admin.py set-user-active USERNAME inactive
python scripts/erp_admin.py set-user-active USERNAME active

# Revoke every active token without changing the password
python scripts/erp_admin.py revoke-sessions USERNAME
```

The administrator cannot be disabled. There is intentionally no user
deletion endpoint, which avoids accidental deletion of audit relationships in
this toy implementation.

### Role commands

```bash
python scripts/erp_admin.py create-role ROLE
python scripts/erp_admin.py assign-role USERNAME ROLE
python scripts/erp_admin.py remove-role USERNAME ROLE
python scripts/erp_admin.py grant-role-tool ROLE BAPI_TOOL_NAME
python scripts/erp_admin.py revoke-role-tool ROLE BAPI_TOOL_NAME
```

Role names must be 2-64 characters, start with a letter, and otherwise use the
same character set as usernames.

### Per-user overrides

```bash
# Add a tool even if no assigned role grants it
python scripts/erp_admin.py grant-user-tool USERNAME BAPI_TOOL_NAME

# Deny a tool even if an assigned role grants it
python scripts/erp_admin.py deny-user-tool USERNAME BAPI_TOOL_NAME

# Remove the override and return to role-based resolution
python scripts/erp_admin.py clear-user-tool USERNAME BAPI_TOOL_NAME
```

`clear-user-tool` does not deny or grant. It removes the user-specific decision,
so assigned roles determine access again.

## 6. Admin HTTP API reference

Automation may call the API directly. First obtain an admin token:

```bash
curl -sS "$ERP_URL/auth/login" \
  -H 'Content-Type: application/json' \
  -d '{"username":"ahad-anzar","password":"replace-this-example"}'
```

The response is:

```json
{
  "access_token": "opaque-random-value",
  "token_type": "Bearer",
  "expires_at": 1790000000,
  "expires_in": 3600
}
```

Send the token to an operation:

```bash
curl -sS "$ERP_URL/admin/create_user" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"username":"buyer","password":"a unique long passphrase"}'
```

All successful admin mutations return `{"ok":true}`. Supported operations and
JSON bodies are:

| Operation | JSON body |
| --- | --- |
| `create_user` | `{"username":"buyer","password":"..."}` |
| `reset_password` | `{"username":"buyer","password":"..."}` |
| `set_user_active` | `{"username":"buyer","active":false}` |
| `revoke_sessions` | `{"username":"buyer"}` |
| `create_role` | `{"role":"purchasing"}` |
| `assign_role` | `{"username":"buyer","role":"purchasing"}` |
| `remove_role` | `{"username":"buyer","role":"purchasing"}` |
| `grant_role_tool` | `{"role":"purchasing","tool":"BAPI_PO_GETLIST"}` |
| `revoke_role_tool` | `{"role":"purchasing","tool":"BAPI_PO_GETLIST"}` |
| `grant_user_tool` | `{"username":"buyer","tool":"BAPI_PO_GETLIST"}` |
| `deny_user_tool` | `{"username":"buyer","tool":"BAPI_PO_GETLIST"}` |
| `clear_user_tool` | `{"username":"buyer","tool":"BAPI_PO_GETLIST"}` |

Log out when finished:

```bash
curl -sS "$ERP_URL/auth/logout" \
  -X POST -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H 'Content-Type: application/json' -d '{}'
```

Never put real passwords or tokens in committed files. In unattended systems,
inject secrets through that platform's secret store rather than placing them in
shell scripts.

## 7. Login, sessions, lockout, and revocation

- Tokens are generated from 32 random bytes and returned only at login.
- SQLite stores only `SHA-256(token)` in `sessions.token_hash`.
- A token expires one hour after login and has no refresh endpoint.
- Every authenticated HTTP request checks token expiry, revocation, and whether
  the user remains active.
- Five failed passwords lock that user for 15 minutes.
- A successful login clears failed-attempt and lockout fields.
- An admin password reset also clears lockout and revokes all user sessions.
- Disabling a user or calling `revoke_sessions` revokes all their sessions.

The login endpoint intentionally returns the same `401 Invalid credentials`
response for an unknown, disabled, locked, or incorrectly authenticated user.
This avoids disclosing which usernames exist.

To obtain a token without placing the password in command history:

```bash
export ERP_USERNAME=purchasing-agent
export ERP_TOKEN="$(python scripts/erp_admin.py login)"
```

The password prompt is written to the terminal while standard output contains
only the token. Clear it when finished:

```bash
unset ERP_TOKEN
```

## 8. Verify a user's MCP access

The included smoke client logs in, uses the MCP SDK over Streamable HTTP, and
logs out automatically.

List only the tools permitted for the user:

```bash
python scripts/mcp_client.py --username purchasing-agent
```

Call a no-argument tool:

```bash
python scripts/mcp_client.py --username purchasing-agent BAPI_VENDOR_GETLIST
```

Call a tool with arguments:

```bash
python scripts/mcp_client.py --username purchasing-agent \
  BAPI_PO_GETDETAIL --arguments '{"po_id":1}'
```

If `ERP_TOKEN` is already set, the script uses it instead of requesting a
password and leaves that session active. Arguments must be one JSON object.

## 9. Connect an agent or MCP client

The general connection settings are:

```text
Transport: Streamable HTTP
URL:       http://127.0.0.1:8000/mcp
Header:    Authorization: Bearer <user token>
Protocol:  legacy / MCP through 2025-11-25
```

Use a dedicated non-admin ERP user for each agent or trust boundary. Grant only
the tools its job requires. Do not give an agent the default administrator's
token merely because setup is easier.

### OpenCode V2

Obtain a token in the same shell that will start OpenCode:

```bash
export ERP_USERNAME=purchasing-agent
export TOY_ERP_TOKEN="$(python scripts/erp_admin.py login)"
```

Add this project-level `opencode.jsonc`:

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "servers": {
      "toy-erp": {
        "type": "remote",
        "url": "http://127.0.0.1:8000/mcp",
        "oauth": false,
        "protocol": "legacy",
        "headers": {
          "Authorization": "Bearer {env:TOY_ERP_TOKEN}"
        }
      }
    }
  }
}
```

OpenCode reloads configuration files after they are saved. Environment values,
however, come from the OpenCode process, so launch it from the shell containing
`TOY_ERP_TOKEN`. Check the connection with:

```bash
opencode mcp list
```

The expected state is `toy-erp connected`. In Code Mode, OpenCode groups the
tools under the normalized server name. If the token expires, obtain a new one,
export it, and start the client process with the updated environment.

Do not use OpenCode's OAuth sign-in for this server. The ERP currently supports
a login endpoint and bearer header, not an OAuth authorization server; therefore
the MCP entry explicitly uses `"oauth": false`.

### Python MCP SDK

The essential client flow is:

```python
import asyncio
import httpx2
from mcp.client.client import Client
from mcp.client.streamable_http import streamable_http_client


async def main():
    token = "obtain this from POST /auth/login"
    async with httpx2.AsyncClient(
        headers={"Authorization": f"Bearer {token}"}
    ) as http:
        transport = streamable_http_client(
            "http://127.0.0.1:8000/mcp", http_client=http
        )
        async with Client(transport, mode="legacy") as client:
            print([tool.name for tool in (await client.list_tools()).tools])
            result = await client.call_tool("BAPI_VENDOR_GETLIST", {})
            print(result)


asyncio.run(main())
```

For an application, perform login in its secret-handling layer, retain the token
in memory, and create a new authenticated MCP connection when the token expires.
Do not hard-code the token in source code or an agent prompt.

### Other agent frameworks

Any framework that supports MCP Streamable HTTP and custom headers can connect.
Configure the `/mcp` URL and add the bearer header. If a framework supports only
stdio MCP or cannot attach HTTP headers, it cannot connect directly; use a
trusted Streamable-HTTP-to-stdio bridge that injects the token outside model
context, or choose a client with authenticated Streamable HTTP support.

### Claude Desktop and similar desktop clients

Use the desktop client's remote Streamable HTTP configuration if that client
supports both remote MCP URLs and custom headers: set the URL to
`http://127.0.0.1:8000/mcp` and the `Authorization` header to
`Bearer <token>`. Configuration formats vary by client version, so follow the
client's current remote-MCP documentation rather than copying an unverified
JSON shape. A client that supports only local stdio servers needs the trusted
bridge described above.

## 10. Auditing and operational checks

`security_events` records:

- successful and failed logins;
- logout;
- every admin mutation;
- successful MCP tool calls; and
- denied tool calls.

Passwords and raw tokens are not included. For local diagnosis, query a copy or
read-only connection to the database:

```sql
SELECT event_time, actor, action, detail
FROM security_events
ORDER BY event_id DESC
LIMIT 100;
```

SQLite table access is effectively full administrative access. Restrict OS and
container-volume permissions on the DB and its backups. Anyone who can alter the
database can replace hashes, grants, or session state.

Recommended remote deployment controls:

- terminate TLS at a maintained reverse proxy;
- expose only the reverse proxy, not port 8000 directly;
- rate-limit `/auth/login` at the proxy;
- restrict `/admin/*` by network policy where practical;
- back up the SQLite volume and test restores;
- rotate agent passwords and revoke sessions after suspected exposure; and
- review `security_events` for repeated failures and denied calls.

## 11. Troubleshooting

### `401` from `/auth/login`

The username/password is wrong, the user is inactive, or the account is in its
15-minute lockout. The public response intentionally does not distinguish them.
An administrator can run `reset-password`, which also clears the lockout.

### `401` from `/mcp` or `/admin/*`

The bearer header is absent, malformed, expired, or revoked. Log in again and
make sure the header is attached to every Streamable HTTP request, not only the
initial request.

### `403` from `/admin/*`

The token belongs to a valid non-admin user. The startup-provisioned account is
an administrator; `create_user` creates non-admin users.

### Tool is missing from an agent

For non-admin users, this is normally a permission issue. Check the exact tool
name, role assignment, role grant, and any user-specific deny. Permissions are
resolved on every list/call, so reconnecting should not be necessary after a
grant, although a client may cache its displayed tool catalog.

### `Tool not available`

The client attempted a tool outside the user's current permissions. A grant may
have been revoked after discovery, or the client may be using a stale catalog.

### The configured super-admin password does not work after changing `.env`

The environment password is used only when that username is first created.
Startup intentionally never resets existing credentials. Use `reset-password`
from another active administrator session; otherwise restore a known-good backup
or deliberately rebuild the database, understanding that rebuilding destroys
its data.

### OpenCode reports an authentication/OAuth error

Confirm the server entry has `"oauth": false`, the `Authorization` header uses
`{env:TOY_ERP_TOKEN}`, and the environment variable was present when OpenCode
started. Then run `opencode mcp list` again.
